1. WHAT IS THIS SYSTEM?
================================================================================

This is a web-based system that allows university administrators, lab
technicians, and lecturers to monitor and manage computer laboratories
remotely from a cloud dashboard.

You can:
  - See which lab PCs are online, in-use, offline, or faulty — LIVE.
  - Track student login/logout automatically (attendance taking).
  - Block prohibited applications (e.g., games, cheating tools).
  - Detect unauthorized USB devices being plugged in.
  - Send remote commands to lab PCs (lock, unlock, message, shutdown).
  - View reports: lab utilization, violation trends, attendance exports.
  - Get real-time alerts when policy violations happen.


================================================================================
2. SYSTEM ARCHITECTURE (How it works)
================================================================================

There are THREE parts working together:

  [LAB PCs] ──── Agent software installed on each PC ────┐
                                                          │  (Socket.IO + REST)
                                                          ▼
  [CLOUD SERVER] ─── Node.js + Express API + Socket.IO ─── MongoDB Atlas
                                                          │
                                                          ▼
  [WEB DASHBOARD] ─── React app used by admins, technicians, lecturers

  - LAB PCs run a small "Agent" program that reports CPU usage, RAM usage,
    the active foreground application, USB events, etc. every few seconds.

  - The CLOUD SERVER receives this data via WebSocket (Socket.IO), stores
    historical telemetry in MongoDB, and pushes live updates to the dashboard.

  - The WEB DASHBOARD is a React single-page application that shows
    everything in real-time through charts, status grids, and alert panels.

  - MongoDB Atlas is the cloud database — you don't need to install MongoDB.
    Your connection string is already configured.

4. HOW TO START THE SYSTEM
================================================================================

The system has TWO parts that need to run at the same time:

STEP 1: Start the Backend Server
---------------------------------
  cd server
  npm install        (only needed the first time)
  npm run dev        (or: node src/server.js)

  You should see:
    MongoDB connected: ac-mo1yjio-shard-00-XX.vbbfkkb.mongodb.net
    Default admin user created (admin@labmonitoring.com / admin123)
    Cron jobs initialized
    Server running on port 5000 in development mode

  The server will be accessible at: http://localhost:5000

STEP 2: Start the Frontend Dashboard
--------------------------------------
  cd dashboard
  npm install        (only needed the first time)
  npm run dev

  You should see:
    VITE vX.X.X  ready in XXX ms
    ➜  Local:   http://localhost:5173/

  Open your browser and go to: http://localhost:5173

IMPORTANT: Both terminals must stay running. Use two terminal windows
or tabs.

--------------------------------------------------------------------------------

  WHAT YOU SEE:

  - Online:          Machines with active heartbeat (agent connected)
  - Active Sessions: Students currently logged into machines
  - Open Violations: Unresolved policy violation alerts
  - Labs:            Number of labs configured
  - Today Attendance: Students checked in today

6.2 LABS (Manage Laboratories — /labs)
--------------------------------------------------------------------------------

  WHAT YOU SEE:
  - A grid of lab cards showing name, location, capacity, and
    how many machines are assigned + online
  - "Add Lab" button to create a new lab
  - "Delete" button on each card (admin only)

  HOW TO ADD A LAB:
  1. Click "Add Lab"
  2. Fill in: Lab Name, Location, Capacity (number of PCs)
  3. Click "Create Lab"
  4. The new lab appears in the grid

--------------------------------------------------------------------------------
6.3 MACHINES (View & Control Lab PCs — /machines)
--------------------------------------------------------------------------------

  WHAT YOU SEE:
  - A filter dropdown to view machines from a specific lab
  - A grid of machine cards, each colored by status:
    █ Green  = in-use (student logged in)
    █ Blue   = online (agent connected, no student using it)
    █ Grey   = offline (heartbeat lost)
    █ Yellow = locked / idle
    █ Red    = fault (offline too long during lab hours)
  - Live CPU %, RAM %, and foreground app from each machine
  - Click a machine card to open the command panel

  HOW TO SEND A REMOTE COMMAND:
  1. Click any machine card
  2. A modal pops up with command options
  3. Type a message (for "message" command) — optional
  4. Click the desired command:
     - Send Message: Shows a pop-up on the lab PC
     - Lock:        Locks the machine's screen
     - Unlock:      Unlocks the screen
     - Shutdown:    Shuts down the machine (admin only)
     - Restart:     Restarts the machine

  COMMAND STATUS INDICATORS:
  - pending:   Command is queued (machine is offline)
  - delivered: Agent received the command
  - executed:  Agent successfully ran the command
  - failed:    Command could not execute

--------------------------------------------------------------------------------

  WHAT YOU SEE:
  - Filter by Lab and/or Date

      Check-out Time, Status (present / left-early / no-checkout)

7. STUDENT FLOW (How students use the lab and how it's tracked)
================================================================================

This section explains the full journey of a student from sitting down at
a lab PC to their attendance being recorded — and how the Students page
fits into it.

--------------------------------------------------------------------------------
7.1 The student's journey step-by-step
--------------------------------------------------------------------------------

  STEP 1 — Student arrives at a lab PC
  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
    The agent on that PC shows a login screen asking for the student's
    Matric Number (or a Guest mode for visitors without matric numbers).

  STEP 2 — Session starts automatically
  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
    When the student enters their matric number, the agent calls
      POST /api/sessions/start
      Body: { "machineId": "...", "matricNumber": "CSC/2020/001" }

    The system then does the following automatically:
      1. If the matric number is NEW → a Student record is auto-created
         (no manual entry needed).
      2. If the matric number already exists → the existing record is
         reused.
      3. A Session is created with status = "active".
      4. The Machine status changes to "in-use".
      5. An AttendanceRecord is created (checkInTime = now).
      6. The dashboard updates in real-time via Socket.IO.

  STEP 3 — During the session (monitoring)
  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
    - The agent keeps streaming telemetry (CPU/RAM/foreground app) so
      the technician can see what the student is doing.
    - Active policies apply: if the student opens a blocked app or
      plugs in an unauthorized USB device, a violation alert fires
      on the dashboard in real-time.

  STEP 4 — Student logs out
  ~~~~~~~~~~~~~~~~~~~~~~~~~~~
    The agent calls
      POST /api/sessions/:sessionId/end

    The system then does the following automatically:
      1. The session gets an endTime and durationSeconds.
      2. The Machine status changes back to "online".
      3. The AttendanceRecord gets a checkOutTime.
      4. The dashboard updates in real-time.

    That's it — attendance is recorded FULLY AUTOMATICALLY. There is
    no manual register to fill.

  STEP 5 — Crash / power loss (edge case)
  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
    If the PC loses power or the agent crashes mid-session, a scheduled
    job (runs every 5 minutes) detects the machine has stopped sending
    heartbeats and:
      1. Auto-closes the stale session as "forcefully-terminated".
      2. Marks the AttendanceRecord as "no-checkout".
    This prevents forever-open sessions when a student just walks away
    or the PC is switched off unexpectedly.

--------------------------------------------------------------------------------
7.2 The Students page (pre-registration & correction)
--------------------------------------------------------------------------------

  The Students page (nav bar → "Students") is for ADMIN and TECHNICIAN
  staff. It is NOT required for attendance to work, but it helps in
  two ways:

  1. PRE-REGISTRATION
     - Load a class list before a practical (e.g. add all 300-level
       students with their names and departments).
     - Then when those students log in, sessions instantly attach to
       their real names instead of a placeholder.

  2. CORRECTION & CLEANUP
     - Edit a student's name, matric number, department, or level if
       there's a typo.
     - Delete wrong or duplicate records.

  Lecturer accounts can VIEW the student list but cannot add, edit, or
  delete students.

  PAGE FEATURES:
    - "Add Student" button → opens the creation form.
    - "Edit" button per row → opens the form pre-filled for updating.
    - "Delete" button per row → removes the student (with confirmation).
    - Total student count shown above the table.
    - Info banner explaining how students get added.

  HOW TO ADD A STUDENT MANUALLY (UI):
    1. Go to Students page.
    2. Click "Add Student".
    3. Fill in: Full Name, Matric Number, Department (optional), Level.
    4. Click "Create Student".
    5. The student appears in the table.

  HOW TO ADD A STUDENT VIA API:
    POST /api/students
    Headers: Authorization: Bearer <token>
    Body: {
      "fullName": "Alice Johnson",
      "matricNumber": "CSC/2021/015",
      "department": "Computer Science",
      "level": "300"
    }

7.4 Live demo tip for your defense
--------------------------------------------------------------------------------

  To demonstrate the full student flow live:
    1. Register a few students on the Students page first.

8. HOW TO ADD MORE DATA
================================================================================

All of the following can be done through the dashboard UI, or via
the REST API directly (useful for testing or bulk import).

--------------------------------------------------------------------------------
8.1 Adding a Technician or Lecturer
--------------------------------------------------------------------------------

  UI Method:
    Go to Users page → Click "Add User" → Fill form → Create

  API Method:
    POST /api/auth/register
    Headers: Authorization: Bearer <admin-JWT-token>
    Body: {
      "fullName": "Jane Smith",
      "staffId": "TECH002",
      "email": "jane@university.edu",
      "password": "securepass123",
      "role": "technician"
    }

  The technician can now log in and manage their assigned labs.

--------------------------------------------------------------------------------
8.2 Adding a Laboratory
--------------------------------------------------------------------------------

  UI Method:
    Go to Labs page → Click "Add Lab" → Fill form → Create

  API Method:
    POST /api/labs
    Headers: Authorization: Bearer <token>
    Body: {
      "name": "Computer Lab 2",
      "location": "Block B, Room 205",
      "capacity": 30
    }

--------------------------------------------------------------------------------
8.3 Adding a Machine
--------------------------------------------------------------------------------

  Machines auto-register when the agent runs (recommended), but you
  can pre-register them manually:

  API Method:
    POST /api/machines/register
    Headers:
      Content-Type: application/json
      x-agent-token: agent-registration-token-default-change-me
    Body: {
      "machineTag": "LAB1-PC02",
      "hostname": "LAB1-PC02",
      "macAddress": "AA:BB:CC:DD:EE:02",
      "ipAddress": "192.168.1.102",
      "os": "Windows 11",
      "agentVersion": "1.0.0",
      "specs": { "cpu": "Intel i5", "ram": "8GB", "disk": "256GB SSD" }
    }

  IMPORTANT: After creating a machine, assign it to a lab using
  the dashboard (Machines page → click the machine → or use the
  API PUT /api/machines/:id with labId in the body).

  Without a lab assignment, attendance records won't be created
  for sessions on that machine.

--------------------------------------------------------------------------------
8.4 Adding a Student
--------------------------------------------------------------------------------

  Students are auto-created when a session starts with a new matric
  number. You can also pre-register them:

  UI/API Method:
    POST /api/students
    Headers: Authorization: Bearer <token>
    Body: {
      "fullName": "Alice Johnson",
      "matricNumber": "CSC/2021/015",
      "department": "Computer Science",
      "level": "300"
    }

--------------------------------------------------------------------------------
8.5 Starting a Student Session
--------------------------------------------------------------------------------

  In production, the Agent handles this (a login kiosk on each PC).
  For testing, use the API:

    POST /api/sessions/start
    Headers: x-agent-token: agent-registration-token-default-change-me
    Body: {
      "machineId": "<machine_mongo_id>",
      "matricNumber": "CSC/2020/001",
      "courseCode": "CSC401",
      "purpose": "Programming assignment"
    }

  What happens automatically:
  1. Student is found or created
  2. Session document is created (status: active)
  3. Machine status changes to "in-use"
  4. Attendance record is created (checkInTime = now)
  5. Dashboard is updated in real-time via Socket.IO

  Ending a session (API):
    POST /api/sessions/:sessionId/end
    Headers: x-agent-token: agent-registration-token-default-change-me

  What happens:
  1. endTime and durationSeconds are set
  2. Machine status changes back to "online"
  3. Attendance checkOutTime is recorded
  4. Dashboard updates in real-time

  Force-ending (from dashboard, by admin/technician):
    POST /api/sessions/:sessionId/force-end
    Headers: Authorization: Bearer <token>

  This marks the session as "forcefully-terminated" and sets
  attendance status to "left-early".

--------------------------------------------------------------------------------
8.6 Creating a Policy
--------------------------------------------------------------------------------

  API Method:
    POST /api/policies
    Headers: Authorization: Bearer <token>
    Body: {
      "name": "Block USB Storage",
      "description": "Prevent mass storage devices",
      "type": "usb-restriction",
      "rule": { "usbClass": "mass-storage" },
      "severity": "high",
      "isActive": true
    }

  The policy is immediately synced to all connected agents via
  Socket.IO so enforcement starts within seconds.

9. REAL-TIME FEATURES
================================================================================

The dashboard uses Socket.IO to update without page refreshes:

  ┌───────────────────────────┬─────────────────────────────────┐
  │ Event                     │ What happens on the dashboard    │
  ├───────────────────────────┼─────────────────────────────────┤
  │ machine:status-changed    │ A machine card changes color     │
  │ session:started           │ Active sessions count goes up   │
  │ session:ended             │ Active sessions count goes down │
  │ telemetry:live            │ CPU/RAM % updates on machine    │
  │                           │ card (every 15 seconds)         │
  │ alert:new                 │ New violation appears in alert  │
  │                           │ list and Violations page        │
  │ alert:updated             │ Violation status changes        │
  │ command:status-changed    │ Command completes               │
  └───────────────────────────┴─────────────────────────────────┘

  The "Live" / "Disconnected" indicator at the top of the Dashboard
  page shows whether this real-time connection is active (green) or
  broken (red).


================================================================================
10. THE MONITORING AGENT (For Lab PCs)
================================================================================

The agent is the software installed on each lab computer. It:

  - Registers the machine with the server on first run
  - Sends heartbeat every 10 seconds (keeps status as "online")
  - Collects CPU/RAM/Disk/Network data every 15 seconds
  - Detects the foreground/active application
  - Checks running processes against blocked-app policies
  - Monitors USB insert/remove events
  - Listens for and executes remote commands (lock, message, etc.)
  - Buffers data locally if the network drops and syncs on reconnect

  HOW TO INSTALL THE AGENT (on a lab PC):

  1. Copy the /agent folder to the lab PC
  2. Edit agent/.env:
     - Set SERVER_URL to the server's actual URL/IP
     - Set AGENT_TOKEN to your registration token
     - Set MACHINE_TAG to a unique tag (e.g., "LAB1-PC05")

  3. Run:
     cd agent
     npm install
     node src/index.js

  4. For production (auto-start on boot):
     - Use node-windows to register as a Windows service
     - Or use PM2: pm2 start src/index.js --name lab-agent
                    pm2 save
                    pm2 startup

  LIMITATIONS:
  - The "usb-detection" and "active-win" npm packages require
    native Windows dependencies and don't work on Linux/Mac.
    On Linux, USB detection and precise foreground app detection
    are gracefully disabled with console warnings.
  - Remote lock/unlock: On Windows, lock uses the OS lock screen
    (rundll32.exe). True remote unlock is not possible on Windows
    without credential entry — this is a documented limitation.

11. SECURITY
================================================================================

  MEASURES IN PLACE:

  - All API routes require JWT authentication (except agent endpoints
    which use a pre-shared registration token).
  - Passwords are hashed with bcrypt (12 salt rounds) — never stored
    in plain text.
  - Rate limiting on auth endpoints: 20 attempts per 15 minutes.
  - Account lockout after 5 failed login attempts (locked for 15 min).
  - JWT access tokens expire in 15 minutes; refresh tokens last 7 days.
  - Silent token refresh on the dashboard — users don't get logged out
    mid-session.
  - Input validation with express-validator on all mutating routes.
  - Helmet.js sets security headers.
  - CORS configured to only allow the dashboard origin.
  - Role checks enforced server-side — never trust the client.
  - Every admin/technician action is logged to the AuditLog collection.
  - Agent registration requires a pre-shared token (configurable).
  - In production, use HTTPS/WSS for all traffic.

  IMPORTANT: Before production deployment, change these values in
  server/.env:
    - JWT_ACCESS_SECRET  (use a long random string)
    - JWT_REFRESH_SECRET (use a different long random string)
    - AGENT_REGISTRATION_TOKEN (use a strong random token)
    - CORS_ORIGIN (set to your actual frontend domain)

  Never commit .env files to git. The .gitignore already excludes them.

12. TROUBLESHOOTING
================================================================================

  PROBLEM:  "MongoDB connection error" on server startup
  SOLUTION: Check that your MongoDB Atlas IP whitelist includes your
            current IP address. In Atlas → Network Access → Add IP Address
            → "Allow Access from Anywhere" or add your specific IP.
            Verify the MONGODB_URI in server/.env is correct.

  PROBLEM:  Dashboard shows "Loading..." forever
  SOLUTION: Make sure the backend server is running on port 5000.
            Check: curl http://localhost:5000/health
                   Should return {"status":"ok",...}

  PROBLEM:  "Access denied" or "Invalid token" when using dashboard
  SOLUTION: Your JWT token expired. Log out and log in again.
            The dashboard has silent refresh but if the refresh token
            also expired you need to re-authenticate.

  PROBLEM:  Machines show as "offline" even though the agent is running
  SOLUTION: The agent must send heartbeats. Check agent logs.
            Make sure the SERVER_URL in agent/.env points to the
            correct server URL (use the actual IP, not localhost,
            if the agent is on a different machine).

  PROBLEM:  Port 5000 or 5173 is already in use
  SOLUTION: Kill the existing process:
            kill $(lsof -ti:5000)
            kill $(lsof -ti:5173)
            Then restart.

  PROBLEM:  Attendance records are empty even after sessions
  SOLUTION: The machine must be assigned to a lab. Without a labId,
            attendance records are not created. Assign the machine
            to a lab via the dashboard or API.

  PROBLEM:  Violations not showing on dashboard
  SOLUTION: Check that policies are active (isActive: true).
            The agent must be connected and running the policy engine
            (it checks processes every 15 seconds with telemetry).
            Violations are debounced — same violation on same machine
            within 5 minutes increments occurrenceCount instead of
            creating a new alert.

  PROBLEM:  CSV export is empty
  SOLUTION: Filter by date and lab to find records. If no attendance
            records exist for the selected filters, the CSV will have
            only headers (which is correct behavior, not an error).
